# Macro meals — نظام المطبخ السحابي

مشروع Next.js واحد يخدم ثلاثة أقسام:

- `/` — الموقع التسويقي العام
- `/admin` — لوحات فريق العمل (عمليات المطبخ، الجودة، الإدارة التنفيذية)
- `/order-app` — تطبيق العميل، قابل للتثبيت على الجوال (PWA)

كل البيانات من قاعدة بيانات حقيقية. ما فيه بيانات تجريبية ولا محاكاة في أي شاشة.

---

## حالة المشروع الحقيقي

المشروع على Supabase **منشأ وجاهز**، والبيانات محمّلة ومتحقّق منها:

| | |
|---|---|
| المشروع | `food-style` — ref `bfgdswrhegpdnesgchfj` |
| المنطقة | `ap-south-1` (مومباي) |
| الرابط | `https://bfgdswrhegpdnesgchfj.supabase.co` |
| الجداول | 16، وRLS مفعّل على 16/16 |
| السياسات | 36 سياسة RLS |
| البيانات | 80 مكوّن · 53 صنف · 457 سطر وصفة · 308 خانة دوران · إعدادات |

البيانات تمّت مطابقتها مع `src/data/ops/*.json` ببصمة md5 لكل جدول — تطابق تام،
لا صف ناقص ولا حرف مختلف. و`supabase/schema.sql` في المستودع مطابق للسكيما
المنشورة فعلياً (بصمة السياسات والمحفّزات متطابقة).

**الخطوة الوحيدة الباقية عليك:** إنشاء حسابك كإدارة تنفيذية — شوف
[٥) أضف حسابات فريق العمل](#5-أضف-حسابات-فريق-العمل) أو `supabase/staff.sql`.
ما سويته بنفسي عشان كلمة المرور تبقى عندك وحدك.

> المفتاح والرابط يُوضعان في `.env.local` محلياً. الملف مستثنى في `.gitignore`
> ولا يُرفع للمستودع أبداً.

## إعداد مشروع جديد من الصفر

الأقسام ١–٣ تحت **منفَّذة أصلاً** على المشروع أعلاه. هي موجودة لو احتجت تبني
مشروعاً جديداً من الصفر (بيئة اختبار مثلاً، أو مشروع بديل).

### 1) أنشئ مشروع Supabase

اذهب إلى [supabase.com](https://supabase.com) وأنشئ حساباً ومشروعاً جديداً.
اختر منطقة قريبة (Frankfurt أو Mumbai أقرب للسعودية) واحفظ كلمة مرور قاعدة البيانات.

### 2) نفّذ السكيما

من لوحة Supabase → **SQL Editor** → **New query**، الصق محتوى `supabase/schema.sql`
كاملاً ونفّذه. ينشئ:

- جدول `staff` بالأدوار الثلاثة، وجدول `customers` مرتبطاً بحسابات المصادقة
- جداول العمليات (المكوّنات، المنيو، الوصفات، الدوران، الإعدادات، البوابات، الإنتاج، السجل)
- جدولَي سلامة الغذاء (سجل الحرارة، دفعات الصلاحية)
- **36 سياسة RLS** تحدد مين يقرأ ومين يكتب إيش بالضبط

### 3) حمّل بيانات العمليات

في نفس SQL Editor، نفّذ `supabase/seed.sql` — يحمّل بياناتكم الفعلية من ملف الإكسل:
**53 صنف · 80 مكوّن · 457 سطر وصفة · 14 يوم دوران**.

الملف idempotent: تقدر تنفّذه مرة ثانية بأمان لو حدّثتم الإكسل. لإعادة توليده:

```bash
python3 scripts/ops/gen_seed.py
```

### 4) اربط التطبيق

من Supabase → **Project Settings → API** انسخ القيمتين:

```bash
cp .env.example .env.local
```

وعبّي:

```
NEXT_PUBLIC_SUPABASE_URL=https://xxxx.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=eyJhbGci...
```

> `.env.local` مستثنى في `.gitignore` — لا ترفعه للمستودع أبداً.

### 5) أضف حسابات فريق العمل

**العملاء يسجّلون بأنفسهم من `/signup`. الموظفون لا — تضيفهم أنت يدوياً**، وهذا مقصود:
لو كان التسجيل مفتوحاً للموظفين، أي شخص يصير مطبخاً أو تنفيذياً بنفسه.

1. Supabase → **Authentication → Users → Add user**
2. حط الإيميل وكلمة المرور، وفعّل **Auto Confirm User**
3. في SQL Editor نفّذ الأمر من `supabase/staff.sql` بعد تبديل الإيميل والدور:

```sql
insert into staff (user_id, role, name, active)
select id, 'executive', 'اسمك هنا', true
from auth.users
where email = 'إيميلك'
on conflict (user_id) do update
  set role = excluded.role, name = excluded.name, active = excluded.active;
```

الأدوار: `executive` أو `kitchen` أو `quality`.
`supabase/staff.sql` فيه كذلك أوامر الإيقاف وتغيير الدور وعرض الموظفين.

هذا مفروض على مستوى قاعدة البيانات لا على مستوى الواجهة: جدول `staff` ما عليه
أي سياسة INSERT أو UPDATE أو DELETE، يعني ولا حساب تنفيذي يقدر يضيف موظفاً عبر
الـ API — مجرّب على المشروع الحقيقي ومرفوض.

### 6) شغّل

```bash
npm install
npm run dev
```

يفتح على `http://localhost:3000`

## الأدوار والصلاحيات

| | الإدارة التنفيذية | المطبخ | الجودة والمتابعة |
|---|---|---|---|
| خطة الإنتاج والمشتريات | عرض | **تعديل** | عرض |
| الوصفات وجدول الدوران | عرض | **تعديل** | عرض |
| القيم الغذائية والحساسية | عرض | عرض | **تعديل** |
| بوابات الجودة (0–6) | — | — | **تعديل** |
| بوابة السعر والهامش (7) | **تعديل** | — | — |
| أسعار المكوّنات | **تعديل** | — | — |
| الإعدادات وهندسة المنيو | **تعديل** | — | — |
| سجل التعديلات | عرض | — | — |
| سجلات سلامة الغذاء | **تعديل** | **تعديل** | **تعديل** |

**الفصل مفروض في قاعدة البيانات نفسها، مو في الواجهة.** أي تعديل خارج صلاحية الدور
ترفضه Postgres حتى لو عُدّلت الواجهة أو استُدعيت الـ API مباشرة.

نقطة مهمة: **ما يُنشر صنف للعميل إلا باتفاق دورين** — الجودة تعتمد البوابات 0–6،
والإدارة التنفيذية تعتمد بوابة السعر (7). ولا دور واحد يقدر ينشر لحاله.

## حالة الأمان

| الطبقة | الحالة |
|---|---|
| تسجيل دخول حقيقي بالإيميل | ✅ Supabase Auth، الجلسة في كوكي HttpOnly |
| الأدوار | ✅ من جدول `staff` عبر جلسة مُوقَّعة — مو من المتصفح |
| حماية `/admin` | ✅ تُفحص في `proxy.ts` قبل إرسال الصفحة + في الـ layout + في قاعدة البيانات |
| Row Level Security | ✅ 36 سياسة على كل الجداول، المنع هو الأصل |
| بيانات العملاء | ✅ كل عميل يشوف صفه هو فقط |
| الكتابة من المتصفح | ✅ كلها عبر Server Actions، والدور يُقرأ على الخادم |
| سجلات سلامة الغذاء | ✅ للإضافة فقط — ما تُعدَّل ولا تُحذف بعد الحفظ، وباسم مُسجّلها |
| تسجيل الموظفين | ✅ مستحيل عبر الـ API — جدول `staff` بلا سياسة كتابة نهائياً |
| الدوال المساعدة | ✅ في سكيما `private` — غير قابلة للنداء من `/rest/v1/rpc` |
| مدقّق Supabase الأمني | ✅ صفر ملاحظات |

### مُتحقَّق منه فعلياً على المشروع الحقيقي

هذي ما هي ادّعاءات — نُفِّذت كاختبارات على قاعدة البيانات المنشورة وكل نتيجة
مرصودة، والبيانات أُرجعت لحالتها بعدها:

| الاختبار | النتيجة |
|---|---|
| صنف بـ 7 بوابات من 8 | الزائر ما يشوفه |
| صنف بـ 8 بوابات | الزائر يشوفه |
| بوابة واحدة تُرفع HOLD | الصنف يختفي فوراً |
| الجودة تعدّل سعر مكوّن | مرفوض برسالة صريحة |
| الجودة تعدّل القيم الغذائية | مقبول |
| التنفيذي يعدّل القيم الغذائية | مرفوض برسالة صريحة |
| التنفيذي يعدّل السعر | مقبول |
| الجودة تختم بوابة السعر (7) | مرفوض |
| التنفيذي يختم بوابة جودة (3) | مرفوض |
| المطبخ يختم أي بوابة | مرفوض |
| عميل يرقّي نفسه موظفاً | مرفوض |
| تنفيذي يضيف موظفاً عبر الـ API | مرفوض |
| عميل يقرأ صفوف عملاء آخرين | يشوف صفه فقط |
| موظف يعدّل أو يحذف قراءة حرارة محفوظة | 0 صفوف — السجل ما يتغيّر |
| موظف يسجّل قراءة باسم موظف آخر | مرفوض |
| زائر غير مسجّل | ما يقرأ أي جدول تشغيلي |

ومع Supabase غير متاح كلياً: الصفحات العامة ترجع 200، وصفحات `/admin` ترجع
تحويلاً إلى `/login` — تفشل في الاتجاه الآمن، ولا صفحة تطيح بخطأ 500.

## البنية التقنية

| الطبقة | التقنية |
|---|---|
| الواجهة | Next.js 16 (App Router) + React 19 + TypeScript + Tailwind 4 |
| قاعدة البيانات والمصادقة | Supabase (Postgres + Auth + RLS) |
| الخط | Cairo، مستضاف محلياً |

**ملفات مهمة:**

- `src/lib/ops/engine.ts` — محرك الحساب: دوال صافية بلا React ولا متصفح، تطابق صيغ
  الإكسل (تغذية، تكلفة، سعر، هامش، حساسية، مشتريات، هندسة المنيو). قابلة للاختبار وحدها.
- `src/lib/ops/server-data.ts` — قراءة بيانات العمليات من قاعدة البيانات.
- `src/app/admin/ops/actions.ts` — كل تعديلات العمليات كـ Server Actions مع فحص الدور والسجل.
- `src/lib/ops/roles.ts` — جدول الصلاحيات (نسخة الواجهة من سياسات RLS).
- `src/proxy.ts` — تجديد الجلسة وحماية المسارات. (اسمه `proxy` مو `middleware` لأن
  Next 16 هجر الاسم القديم.)
- سكيما `private` في قاعدة البيانات — الدوال المساعدة (`is_staff`, `has_role`,
  `current_staff_role`, والمحفّزات). PostgREST يكشف `public` فقط، فما هي قابلة
  للنداء من الـ API، والسياسات تناديها عادي.
- `supabase/schema.sql` — السكيما والسياسات (36 سياسة RLS).
- `supabase/seed.sql` — بيانات العمليات، مُولَّدة آلياً.
- `supabase/staff.sql` — إضافة وإيقاف وتغيير أدوار الموظفين.
- `supabase/cleanup.sql` — حذف دالّتَي اختبار متبقّيتين (سطران، مرة واحدة).
